# workflows skill — Changing an existing workflow, with Undo

Part of the workflows skill (`SKILL.md`). Sections keep their numbers; "section N" means the section with that number in `SKILL.md` or in another file under `references/`.

## 5. Change an existing one: change it directly, with "Undo"

- **In a DM:** ordinary changes are applied directly, with no confirmation card and no draft (G2-RP.6, G2-OM.7). Call the same write actions as the web, with the on-behalf header: change one step `update_step` (`wf step update <sid>`), save all steps `replace_steps` (`wf step replace <id>`), add a step `add_step`, delete a step `delete_step`, reorder `reorder_steps`, triggers `create_trigger` / `update_trigger` (deleting one: see the next point), settings `update_workflow_settings`. Read the current revision first and send it as `if_match`. If one message changes several steps, combine them into one `replace_steps`.
- **Say "在改" first.** Before any lookup or write for a change request, reply one line in that conversation: 「在改」 (in their language: "On it"); at tier 深 that line is 「在做，约 HH:MM 交。」 instead (section 1-2). **Send it without waiting for the send to return**: pipe it through `~/zylos/workspace/zylos-workflows/scripts/ack.mjs` (installed with this skill, next to `register.mjs`), which hands it to your send command in the background and returns at once (`printf '在改' | node ~/zylos/workspace/zylos-workflows/scripts/ack.mjs -- <your send command …>`; send output and exit code go to `$TMPDIR/wf-ack.log`, readable only by you). A failed or slow send never holds up the write; from starting to handle the message to the write stays within 5 seconds (#626). The server's "Changed, saved as vN" sentence comes after the write as usual; the first line never says it is done (#575).
- **Fixed recipe: change one step** (e.g. "change step 2's name to Manager review", or "change this" with the steps window open). Four calls, one write:
  1. Reply 「在改」 through `ack.mjs`, without waiting (above).
  2. `wf butler said <message_id>` with `--on-behalf '<json>'` (section 1-1) → `workflow_id`, and `step_n` if they were editing a step. Typed directly in OpenMax: work out the workflow and step as section 1-1 says.
  3. `wf step list <workflow_id>` → the row whose `seq` is that step number; take its `id` as `<sid>`. If no row or several rows match what they said, ask which step; do not guess. If the list comes back with `blocked.reason = BUTLER_SPEAKER_REQUIRED`, that only says you read it without saying whom for: `can.edit` is true, carry on with step 4 (it carries the on-behalf header). Any other `blocked.reason` (`viewer`, `BUTLER_LEVEL_TOO_LOW`, …) means the steps cannot be changed through you (`can.edit` is false); then reply with its `reason_plain`. Never tell the person you only have view access because of `BUTLER_SPEAKER_REQUIRED` (#851).
  4. `wf step update <sid>` with `--on-behalf '<json>'` and `--body '<fields>'`, only the fields that change. `--body` takes the JSON inline (or a file path); leave out `--if-match`, the CLI reads the step's revision itself; a new idempotency key is made for you. Then paste the server's sentence as-is.

  ```
  wf step update 0193d2c4-… \
    --on-behalf '{"speaker_openmax_member_id":"01a1635b-…","source_message_id":"1790220996596","conversation_id":"019f659d-…"}' \
    --body '{"name":"Manager review"}'
  ```
  On 409 `STALE_REVISION` (someone saved in between), run step 4 once more unchanged (it reads the new revision); 202 `BUTLER_CONFIRM_CARD`, `BUTLER_WEB_ONLY` and the D-108 kinds as the bullets below say; any other error, reply with `reason_plain`. Several steps in one message: one `replace_steps` instead (below).
- **Step fields** (the same fields `update_step` / `add_step` / `replace_steps` take, W6-ED.9 to W6-ED.16; send only what changes; the list fields are always sent **whole**, they replace what is there):
  - **Who checks it: `gates`** (W6-ED.10), on AI and person steps: `[{member_id | at_start: true, due}]`, level 1 first. A fixed person: `member_id`; 「发起时指定」: `at_start: true` and no `member_id`. `[]` = nobody checks it. **There are no review steps any more**: "add a manager review after step 2" means adding a level to step 2's `gates`, never a step of its own; writing `kind = review` is refused (422 `KIND_RETIRED`). To add or remove one level, read the step's current `gates` (`wf step list`), change that list and send it all back.
  - **Who checks it cannot be the one who did it**: a level whose person does this step (including the people working on it together) or already checked an earlier level is refused (422 `TARGET_INVALID` with `details.rule` = `GATE_IS_EXECUTOR` / `GATE_PRIOR_DECIDER`, W6-I.9). Paste `reason_plain` and ask who else; do not pick someone yourself.
  - **Several people on one step: `co_members` + `co_mode`** (W6-ED.11): `co_members` are the others' member ids (the main one stays in `worker` / `fixed_member_id`; repeating them is 422 `BAD_BODY`). `co_mode`: `lead_split` split it up, the main one leads (default) / `each_submit` everyone hands in their own, it moves on when all are in / `first_claim` whoever takes it first does it.
  - **Deadline: `due`** (W6-ED.12), on person steps and on each `gates` level: `{"mode":"by","day":"same_day"|"next_day","at":"HH:MM"}` ("by 17:00 today") or `{"mode":"within","amount":N,"unit":"minute"|"hour"|"workday"}` ("within 2 working days"). On a person step use `due`, not the old `due_within`; sending both is 422 `BAD_BODY`.
  - **What it hands in: `outputs`** (W6-ED.13): `[{id?, name}]`, a name is at most 40 characters. Renaming one keeps its `id` (send it), so later steps that `@`-quote it follow; a new one has no `id`. Dropping one that a later step quotes is refused (422 `REF_BROKEN`, `details.step` is the step that quotes it): say which step quotes it and ask.
  - **Quoting earlier results in 「怎么做」** (W6-ED.16): in `description`, `{{ref:<step_id>:<output id>}}` quotes one item a step before this one hands in (`all` for a step without `outputs`); `{{ref:start:<key>}}` quotes a start-form field. Use the step `id` from `wf step list`, never the step number.
  - **`role_label`** (W6-ED.14): a role placeholder of at most 8 characters ("财务") for a step nobody is picked for yet; picking a person or AI clears it.
  - **`end_on_judge`** (W6-ED.9), AI steps only: the AI may end the run after judging. Turning it on when people check or work on later steps is a high-risk change (W7-S.2): only when they asked for exactly that, and if the server answers with a confirm card, post it as the D-108 bullet below says.
  - **Where it goes next: `next_step_id`** (W6-ED.15): another step's `id`; `null` = the next one. A step that no longer exists is 422 `NEXT_STEP_GONE`; a loop back with no AI step in it that may end the run is 422 `LOOP_NO_END` (`details.steps`): paste `reason_plain` and ask how the loop should end.
- **Adding or changing a step from one sentence in your DM** (W7-SAY.1, W7-SAY.2, W7-SAY.3, W7-SAY.5, W7-SAY.6): someone says "add a step: every Monday Finance Assistant sums up the week's invoice checks for me", or "change step 2 to Lova".
  - Fill every field you can from the sentence (who does it, what it hands in, deadline, who checks it) and write it straight away, same as any ordinary change. Do not ask about each field first.
  - In your own words, name people and AI members by their names (「财务助理 汇总这周的发票核对结果…」「周婷 把付款记录补进台账…」), never ids; a `at_start` seat is 「发起时指定的人」 (W7-SAY.3).
  - Whatever you guessed rather than heard, say so in one line with the reason, e.g. 「谁来做按 财务助理 填的：上次核对发票的是它，不对直接说」 (W7-SAY.2).
  - If the sentence says when it should run ("every Monday"), that is not part of the step: the trigger belongs to the whole workflow. Say 「每周一跑要改触发，触发是整条工作流的」 and change the trigger as its own change (`update_trigger` / `create_trigger`, the schedule shapes below), only if that is clearly what they meant (W7-SAY.5).
  - Then paste the server's sentence as-is: "before → after" with "Undo" (W7-SAY.6). Swapping the AI member on an existing AI step (the new one will see this step's input) is not applied by you: the server answers with a confirm card (D-108 bullet below); new steps, people, and wording changes are applied directly.
- Adding a learned item when someone asks you to ("remember this for next time"): `add_workflow_learned` (`wf learned add <id>`) with the on-behalf header and body `{"text":"…"}`. Its `--if-match` is the `revision` from `get_workflow_settings` (`wf settings get <id>`), not from `wf workflow get`: the workflow's revision gets 409 `STALE_REVISION` even when nobody saved in between. Paste the server's sentence as-is.
  - **「记住这个：……」/「以后都这样：……」** (P2.1-T3-LN.4): save the sentence they said, as one item, in the same turn. If they only said 「记住这个」 without saying what, ask which sentence to remember; do not guess (same as PR.15).
  - **Said in another channel** (Lark, Telegram, WeCom…; P2.1-T3-TR.8): it is a change from another channel, so do exactly what "Changing a workflow from another channel" above says: the same `add_workflow_learned` / `edit_workflow_learned` / `remove_workflow_learned` call with `on_behalf = {"channel":{…,"said":"<the sentence said to you, verbatim>"}}` and no speaker. Do not run the identification tool for it and do not send an OpenMax-style header. Calling with no on-behalf header at all gets 403 `BUTLER_SPEAKER_REQUIRED` and saves nothing. The server saves nothing then: it puts a card showing the sentence on the workflow's page, and someone who can edit confirms it on the web. Reply only the 202 `EXT_CARD_ISSUED` sentence (G2-EX.2). A 422 (`SECRET_IN_TEXT`, `LEARNED_TOO_LONG`, 20 items) means no card: paste `reason_plain` as-is.
  - Before adding, compare with the existing learned items (`get_workflow_references`, `wf reference list <id>`, the `learned` part). If one says the same thing and is marked `by_butler`, update that one instead (`edit_workflow_learned`, `wf learned edit <id> <lid>`, same `--if-match` rule) with the revised full text. If the same thing is already there without `by_butler` (a person edited it), leave it and tell them it is already there. An item a person removed earlier is **not** a reason to refuse: they are asking now, so save it.
  - The reply is `butler_said.text` as-is (「记下了：<全文>，存成 vN」) with its 「撤回」 action (`butler_said.actions`); the item is marked 「管家记的」 by the server. If the response also has `kb_notice`, post that sentence once after it (KB.3).
  - Refusals come back as 422 / 403 with `reason_plain`; paste it as-is and save nothing: 「一条最多 500 个字，这条有 N 个」 (LN.11), 「学到的事已经 20 条了，先去掉一条再让我记」 (LN.12), anything that looks like a key or password is refused whole (`SECRET_IN_TEXT`), and someone who cannot edit this workflow gets the 403 sentence (G2-RE.10).
- **No place to keep it yet** (P2.1-T3-KB.9, CR-430): adding a principle (PR.15, `update_workflow_settings`), a learned item (LN.4, `add_workflow_learned`) or a written reference (REF.12, `add_workflow_reference_note`) can return 422 `KB_UNAVAILABLE` with `details.cause = no_project`. This means the workflow has no 「运行记在」 Project yet and none of the three has been placed anywhere, so nothing was saved. Reply with `reason_plain` as-is (「先选这条工作流运行记在哪个 Project，选好我再记」) plus the link in `details.href`. Do not build a link yourself, and do not use `details.target`: that one is for the web page. Keep what they asked you to add in the conversation. When they then say 「记上」 (or that they have picked the Project), call the same action again with the same text, once. If it still returns `no_project`, reply the same way again; do not retry on your own.
- **Schedule triggers** (`kind = schedule`; also the `triggers` in a draft, D1-ED.4, D1-ED.21): `schedule` takes exactly one shape, picked by `freq`:
  - `daily` / `workdays`: `{freq, time}`; `weekly`: `{freq: "weekly", weekdays, time}` with `weekdays` ISO numbers, Monday = 1 … Sunday = 7; `monthly`: `{freq: "monthly", month_day, time}` with `month_day` 1 to 28. `time` is `"HH:MM"`, 24-hour, minutes in steps of 5.
  - `every`: `{freq: "every", every: {n, unit: "minute"|"hour"}}`, optional `window: {from, to}` and `workdays_only`; no `time`.
  - `cron`: `{freq: "cron", cron: "<5 fields>"}` — minute hour day month weekday, digits and `* , - /` only (no seconds, no `MON`/`FRI`, no `@every`); no `time`, `weekdays` or `month_day`. Use it only for what the shapes above cannot say (e.g. "first day of each quarter 09:00": `0 9 1 1,4,7,10 *`).
  - Optional `tz` (IANA name); leave it out to use the org's time zone.
  - Prefer the plain shapes: "每周五 17:00" is `{"freq": "weekly", "weekdays": [5], "time": "17:00"}`, not cron; "工作日 09:00" is `{"freq": "workdays", "time": "09:00"}`; "每 2 小时" is `{"freq": "every", "every": {"n": 2, "unit": "hour"}}`.
  - On 422 `SCHEDULE_INVALID`, `reason_plain` says which field to use and gives the right form: fix the body that way and call again once; do not paste it to the person unless it is about what they asked for (e.g. the interval is shorter than the org allows).
- **Deleting a trigger is the exception: confirm first** (D1-I.11, D1-X.4). Say exactly which trigger (its one-line summary, e.g. "every weekday 09:00") and the consequence for its kind, the same sentence as the web (D1-ED.24): "After deleting it, no more runs start from it; runs already started finish as usual", plus for "after X finishes" "the runs of X still in progress will not start this one either", for inbound webhooks "the push address stops working at once; pushes from outside get 404", for chat start "you can no longer ask me to start this one", for watches "I stop watching at once". Only after the speaker clicks / says yes to that message, call `delete_trigger` (`wf trigger delete <tid>`) with the trigger's revision as `if_match` and the on-behalf header; who may delete is the same level as changing that kind of trigger. "Undo" recreates it from the settings before the delete as a **new** trigger, except an inbound webhook: undoing that delete is not done in chat (the server returns 403 with `details.rule = BUTLER_REVERT_PAGE_ONLY`); reply with the server's sentence (undo it yourself on the web) plus the web link; the new push address and secret are shown there to that person once and must be set again in the outside system (CR-254, D1-WH.15).
- Reply with the server's sentence from the response ("Changed, saved as vN" + each "before → after" + "Undo", G2-RE.2). Changes are not blocked while the workflow is enabled or has runs in progress; the trailing half-sentence about that also comes from the server (G2-RE.3).
- The D-108 kinds that cannot be undone (changing the steward, adding a system to a step, widening sharing, transferring ownership, setting a delegate approver, accepting an out-of-scope item …) are **never applied by you**: call the write as usual with the on-behalf header; the server writes nothing and returns 202 with `code = BUTLER_CONFIRM_CARD` and a confirm card (`details.card_id`, `details.preview`, `details.consequences`, `details.expires_at`, `details.href`). Paste `reason_plain` as-is, then the link exactly as 「[去确认 ›](<details.href>)」; do not build the link yourself, do not retry, and never call `/butler/confirm` yourself: only the person, in their own web session, can confirm (G2-RE.24, D-569). They type the workflow name there for a transfer and write a reason there for accepting an out-of-scope item; do not ask for either in the chat. If the speaker's level is not enough, there is no card: paste the 403 sentence (G2-RE.10).
- Some changes are not done for anyone and get no card: deleting the workflow (except 「撤回」 of the one you just created from their DM draft, not yet run, section 3), inbound webhooks, watches, sharing outside the org, review decisions, high-risk items on a workflow that does not exist yet (creating one), and, when you are an AI talking in a run's step DM rather than the steward, any of the D-108 kinds (G2-RE.5, CR-464). The server returns 403 `ACTION_NOT_ALLOWED` with `details.rule = BUTLER_WEB_ONLY` and writes nothing (recognize it by `details.rule`, not `code`): give the person the link in `details.href` to click on the web; do not retry and do not try another action. Reply exactly 「[这个要你自己在网页上操作 ›](<details.href>)」, one message, nothing else in it (no extra sentence before or after, no other link): the web shows it as a clickable link only when it is word for word this sentence plus the link the server gave you (G2-RE.5, CR-451); any other wording shows as plain text.
- Inbound webhook triggers (D1-WH.15): only people who can manage the workflow decide; if their level is not enough, reply with `reason_plain`.
  - Creating one, switching another trigger kind to an inbound webhook, or rotating the secret (the old secret stops working at once and cannot be restored): never on someone's behalf. When the server returns `BUTLER_WEB_ONLY`, reply "You need to do this yourself on the web ›" with `details.href` (G2-RE.5). Changing only its instructions is an ordinary change and is applied directly: `update_trigger` (`wf trigger update <tid>`).
  - Rotating the secret is web-only for everyone, including you acting as yourself (`rotate_webhook_secret` / `wf trigger rotate-secret` always returns `BUTLER_WEB_ONLY`): do not call it to "fix" pushes; send the person the same reply with `details.href` (D1-WH.2, D1-WH.15).
- Watch triggers (`kind = watch`, "keep an eye on X and start this workflow when Y happens", D1-WA.1 to D1-WA.6): only people who can manage the workflow decide; if their level is not enough, reply with `reason_plain`.
  - Creating one, switching another trigger to a watch, or changing what it watches (`watch.ask`) or its daily run cap (`watch.max_runs_per_day`): never on someone's behalf. When the server returns `BUTLER_WEB_ONLY`, reply "You need to do this yourself on the web ›" with `details.href` (D1-WA.5). Changing only its `instruction` is an ordinary change: `update_trigger`.
  - When you are this workflow's butler, you may change only how you check (the plan, 1 to 100 characters, e.g. "don't check at night"), as yourself without the on-behalf header: `change_watch_plan` (`wf trigger watch-plan set <tid> <plan>`). It never changes what is watched, the caps or the next check time. Tell the person what you changed in one line (D1-WA.8).
  - To answer "what has it seen lately", read `list_watch_checks` (`wf trigger watch-checks <tid>`, manage level only); quote `reason_plain` and the run number, never `situation` text to anyone without manage level (D1-WA.6, D1-WA.13).
  - Secrets never go into the conversation: do not paste them, repeat them, or ask anyone to send them to you (D1-WH.13, D1-WH.15).
- If it is unclear what to change, or several places match: ask first; do not guess (G2-RE.2).
- Personal reminders (1.3-AV.10), DM only: "don't DM me when Lin nudges me" → `mute_reminder_member` (`wf me reminders mute-member <member_id>`); "mute X no more" → `unmute_reminder_member`; "don't DM me when this workflow finishes" → `mute_reminder_workflow` / `unmute_reminder_workflow` (`<workflow_id>`), with the on-behalf header; it always changes the speaker's own settings, there is no "for whom" field. If the name matches several people or workflows, or none, ask which one first; never guess (G2-RE.2). Paste `butler_said.text` as-is; "Undo" → `undo_reminder_edit` (`wf me reminders undo <undo_id>`), paste its `plain` or `reason_plain` as-is (G2-RP.7).
- My tags (G2-RE.25), in the speaker's DM with you or the butler panel only (in a group the server refuses with `DM_ONLY`; reply with its `plain` as-is, don't try again): "tag expense approval and invoice request with 月结" / "remove 月结 from …" → `apply_my_tag` (`wf me tags apply --file <path>`, body `{"tag": "月结", "workflow_ids": [...], "on": true|false}`), with the on-behalf header. Resolve the names to ids from workflows the speaker can see; if a name matches several or none, ask which one first, never guess. It only ever tags the speaker's own tags, nobody else's. Paste `butler_said.text` as-is (it already says "another N not found"); "Undo" → call `apply_my_tag` again with the response's `undo` object as the body (`{"tag_id", "workflow_ids", "on"}`). Renaming or deleting a tag is not done in chat: reply 「改名、删掉在工作流列表「管理标签 ›」里」.
- Approver while away (1.2-DL.4), DM only, with the on-behalf header; it is always the speaker's own setting, there is no "for whom" field:
  - Set it or widen it ("let Zhang Min approve for me until Friday", a later end date, more workflows): `set_delegation` (`wf me delegation set --file <delegation_json>`, body `{delegate_member_id, from, until?, scope: "all" | "workflows", workflow_ids?}`). The server never saves a widening from you: it returns 202 `BUTLER_CONFIRM_CARD`; paste the card's link as-is ("Confirm ›"), the person confirms on the web (G2-RE.24). Never send `dry_run` or `confirm_digest`.
  - Narrow it (an earlier end date, fewer workflows) with the same `set_delegation`, or turn it off ("I'm back, turn it off") with `close_delegation` (`wf me delegation close`): saved directly; paste `butler_said.text` as-is (it says what it is now, or how many items came back to them).
  - "Undo" → `undo_delegation` (`wf me delegation undo <undo_id>`): undoing a narrowing widens it again, so it returns a confirm card like above; paste it as-is. On 409 `DELEGATION_UNDO_STALE`, paste `reason_plain`.
  - If the name matches several people or none, ask which one first; never guess (G2-RE.2). On `BUTLER_WEB_ONLY`, reply "You need to do this yourself on the web ›" with `details.href`.
- @-mentioned in a group to change something: reply "Please DM me or change it on the web" (G2-OM.7).
